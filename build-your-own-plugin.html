Answer four questions before you open Claude Code.

  1. What decision does your team make repeatedly? Pick something that requires judgment — not just a task. If two experienced people could look at the same information and reach different conclusions, it’s a good candidate.
  2. What information do they use to make that decision? List what they look at today: code, documents, tickets, tests, configuration, or knowledge that isn’t written down yet.
  3. What requires judgment, and what can be checked with a rule? Put anything that requires interpretation in the skill and agent. Put clear, repeatable pass/fail checks in a hook. If you don’t have a true pass/fail check, don’t add a hook just to have one.
  4. Who needs the answer, and what do they need to know? Design the output for that person. What do they need to see to make the next decision?

Worked example — an integration engineer at a regional health plan. Change Scout answers one recurring question: what breaks if we change this? Here is a different one from the same team, put through the four questions.

1 · The decision
Is this enrollment service change ready for Thursday’s change-advisory review?
2 · The information
What changed since the last release, test results, database migration files, deployment settings, and the on-call runbook.
3 · Judgment or rule
Judgment: could an on-call engineer actually carry out the rollback plan at 2am? Rule: every database migration has a matching rollback file.
4 · Who needs it
The release manager — ship, ship with conditions, or don’t ship, and what has to happen first.

Check it by behavior. You never have to read the code Claude wrote — but some of these you run yourself and some you ask Claude to do, so each one says which.

  • Claude Code recognizes the plugin. Three steps, in your terminal, from inside your new plugin folder. 1. Check the files are shaped correctly. claude plugin validate . --strict 2. Start Claude Code and point it at your folder. Being inside the folder is not enough — without this it loads no plugin and your command will not exist. claude --plugin-dir . 3. Type a forward slash and look for your command in the list that appears.
  • The specialist actually ran. Make sure Claude Code shows your specialist agent running before you see the final answer.
  • It didn’t change anything it wasn’t supposed to. If your plugin is only meant to analyze or report, make sure it didn’t change any project files. git statuslists files that have changed — or just ask Claude whether anything did If files changed unexpectedly, the specialist may have been given permission to edit them. Ask Claude to review and reduce its permissions.
  • The specialist doesn’t follow instructions it finds inside your project. Put a test instruction in a project file telling the specialist to ignore its job. It should flag the instruction, not follow it.
  • The answer has the structure you asked for. Make sure the final answer includes the sections and information you specified.
  • If you built a hook, it behaves three ways. Ask Claude to break the rule on purpose and you get a clear message; ask it to put the file right and the check goes quiet; ask for a change the rule doesn’t apply to and it stays quiet. Ask Claude rather than editing the file yourself. A hook watches what Claude does, so an edit you make in your own editor never reaches it — and a silent hook looks broken when it is only unaware.
  • It beats plain Claude Code at the job you built it for. Run the same request three times without your plugin loaded, then three times with it — three each way, because you are checking for consistent behaviour rather than one lucky run. Decide what a good answer looks like before you read either set. If the plugin isn’t better, it’s the method that needs work — not the wiring.

Team method SKILL skills/release-method/SKILL.md

Every skill and agent file opens with a block fenced by --- lines. That’s the settings section — Claude Code reads it to learn what the file is. Everything after it is instructions, written normally.

---
name: release-method
description: How this team decides whether a change is ready to release — what
  to check, in what order, and what the answer must contain.
---

# Release readiness

## Work these in order
1. **Scope** — what changed since the last release, and which teams does it touch?
2. **Data changes** — anything changing how data is stored? Can it be undone?
3. **Configuration** — any new setting that has to exist before this works?
4. **Rollback** — if this fails at 2am, what does the on-call person actually do?
5. **Coverage** — do the tests cover what changed, or only what didn't?

## Two rules
- **If you can't find something, say so.** Name what's missing and who could
  answer it. Never fill a gap with a plausible guess.
- **Point to where you found it.** File and line. A claim with no source is
  an opinion.

## The report
1. **Recommendation** — ship / ship with conditions / don't ship. One sentence.
2. **What's changing** — plain language, for someone who hasn't read the code.
3. **Risks** — each marked [Blocking|Material] and [Confirmed|Claimed|Unknown].
4. **What has to happen first** — and who owns it.
5. **What I couldn't determine** — and who to ask.

Under 600 words. This is for a decision, not a code review.

Those [Confirmed|Claimed|Unknown] marks are worth stealing. Confirmed means the code proves it. Claimed means a document says so and nothing corroborates it. Unknown means nobody could tell. Keeping those apart is most of a report’s value.

Deterministic rule HOOK hooks/hooks.json + scripts/check-migrations.sh

Two files. One says when, one says what.

{ "hooks": { "PostToolUse": [ { "matcher": "Write|Edit", "hooks": [
  { "type": "command",
    "command": "\"${CLAUDE_PLUGIN_ROOT}/scripts/check-migrations.sh\"" }
] } ] } }

${CLAUDE_PLUGIN_ROOT} means “wherever this plugin folder happens to live.” Keep the quotes around it. Mine were missing, my folder path contained a space, the path got cut in half, and the check quietly did nothing while reporting success every time. A check that silently passes is worse than no check at all.

TriggerGood forCan it stop the action?
PreToolUsePreventing somethingYes — the only one that can stop a tool call
PostToolUseChecking a result after a file changesNo, but your message goes back to Claude, which usually fixes it immediately
UserPromptSubmitAdding standing context to every requestYes — but it stops the prompt, not a tool call
SessionStartLoading something once at the startNo

This script warns when a database change arrives without a matching undo. After creating it, run chmod +x scripts/check-migrations.sh to mark it runnable.

#!/usr/bin/env bash
# Warn when a migration lands without a matching rollback file.
set -euo pipefail

FILE=$(node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{
  try{console.log(JSON.parse(s).tool_input?.file_path||"")}catch{console.log("")}})')

case "$FILE" in */migrations/*.sql) ;; *) exit 0 ;; esac
[ -f "${FILE%.sql}.down.sql" ] && exit 0

echo "Migration has no rollback: $FILE" >&2
echo "Expected: ${FILE%.sql}.down.sql" >&2
exit 2

You do not need to be able to write this. Claude will. What it does, in order: find out which file just changed; if it isn’t the kind we care about, stop and report success; if the matching undo file already exists, stop and report success; otherwise print a message and finish with the number 2, which is how a script tells Claude “this failed” — and the message goes back so it can be fixed.

Running an outside tool SECURITY the one place a mistake has real consequences

Everything above is mechanics. This is where I got it wrong twice.

First: never let a hook download anything.

My first version fetched a document validator from the internet and ran it — automatically, every time anyone saved a contract file. Two problems. Code I had never seen could run on my machine because I edited a document. And the version wasn’t pinned, so what ran could silently change from one day to the next.

Instead: install one exact version deliberately, once. Pin it with no version range, commit the lock file so you would know if you ever received something different, install with npm ci --ignore-scripts so the package can’t run its own setup code — and have the hook refuse rather than fetch.

[ -x "$TOOL" ] || { echo "Run 'npm ci --ignore-scripts' first." >&2; exit 2; }

Then: ask what that tool reads.

This is the subtler one, and I missed it on the first pass even after fixing the download. The tool was now pinned and trusted. But when it started, it looked for its own settings file — and it was finding that file inside the project being examined. Many settings formats can load add-ons, and add-ons are code. So a project could hand my trusted tool a settings file that said “run my code first,” and it would.

You’ve vetted the inspector, and then you let the building being inspected hand him his instructions on the way in. The fix is to point at your own settings file explicitly, so the tool never goes looking:

"$PLUGIN_ROOT/node_modules/.bin/some-linter" \
  --config "$PLUGIN_ROOT/linter-config.yaml" "$FILE"

The general lesson, which outlives this example: pinning the program you run is only half of it. You also have to control what that program is allowed to load.
